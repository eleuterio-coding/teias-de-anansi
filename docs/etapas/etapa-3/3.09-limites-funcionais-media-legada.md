## 2. Contrato comportamental demonstrado das Rules

Em ambas as versões das Rules (baseline e proposta), usando **identidades e documentos inteiramente fictícios**:

| Cenário | Resultado |
| --- | --- |
| Mestre lê metadados e chunk de mídia com campaignId **ausente** | PERMITIDO |
| Mestre atualiza chunk de mídia com campaignId ausente | PERMITIDO |
| Mestre atualiza os metadados do documento de mídia com campaignId ausente | **NEGADO** |
| Mestre exclui documento de mídia com campaignId ausente | PERMITIDO |
| Depois da exclusão, chunk remanescente pode ser lido por Mestre/Jogador | **NEGADO** (não há mais documento pai) |
| Jogador lê mídia/chunk sem campaignId | **NEGADO** |
| Mestre lê mídia/chunk de campanha histórica cujo documento não existe | PERMITIDO |
| Jogador lê mídia/chunk de campanha histórica inexistente | **NEGADO** |
| Jogador lê apenas mídia/chunk de sessão atribuída | PERMITIDO |
| Jogador lê mídia/chunk de outra sessão | **NEGADO** |

**Implicação:** a leitura antiga pelo proprietário continua possível, mas **edição de metadados de mídia realmente sem campo campaignId não está disponível**, já na baseline. Mídias com campanhaId null foram testadas separadamente. Isso é uma limitação funcional legada concreta, não uma falha introduzida pela Rules proposta. Não inventar que todas as operações do legado são compatíveis.

**Atenção ao chunk órfão após deletar metadados:** a leitura é negada pela regra baseada na existência do pai, mas não há evidência de exclusão física em cascata. Qualquer rotina de exclusão/limpeza precisaria tratar subcoleções explicitamente. Nenhum chunk real foi excluído.

## 3. Limite real da interface existente

A inspeção direta de `src/app/pages/SectionPlaceholder.tsx` mostra a mensagem `Esta área ainda não possui conteúdo disponível.`. Os arquivos de interface desta etapa incluem login, administração de usuários e páginas provisórias, mas **não uma interface completa de mídia legada para homologar imagens/chunks ponta a ponta**. Portanto, não é tecnicamente honesto afirmar que a visualização/edição antiga está validada pela UI da versão atual.

A Etapa 3.09 pode comprovar **acesso e isolamento** de contas, escopo de dados e comportamento emulado. Homologação visual de todas as mídias do Hub legado exige implementação/integração dos respectivos módulos e testes separados. Não preencher `LEGADO_VALIDADO` como se isso comprovasse funcionalidades que ainda não existem.
