## 1. Barreiras de aprovação

A presente autorização **permite apenas preparar, revisar, testar e documentar**. Para qualquer execução futura, apresentar ao usuário **duas ações exatas e independentes**:

- **Aprovação A — Firebase:** publicar a candidata revisada de Firestore Security Rules no projeto existente, depois de pré-requisitos verificados e backup da release atualmente publicada. Isso **não** autoriza alterar usuários, senhas, vínculos ou documentos.
- **Aprovação B — site atual:** substituir o artefato publicado no GitHub Pages existente pelo build aprovado da branch, sem criar repositório nem outros ambientes. Qualquer merge para `main` exige aprovação adicional e explícita se não estiver incluído na autorização de publicação.
- Publicar temporariamente uma página de manutenção no mesmo endereço, se necessário, também depende de aprovação que a inclua.

Se faltar qualquer aprovação ou houver divergência no pré-voo, **parar**. Não executar nada automaticamente por CI: a workflow `verify-etapa-3.yml` deve permanecer **sem deploy, secrets remotos ou acionamento de produção**.

## 3. Sequência proposta após aprovações A e B

**Atenção: Firebase Rules e GitHub Pages não oferecem uma transação única.** Uma breve janela de indisponibilidade pode ser necessária porque o Pages antigo possui consultas de lista que a regra nova bloqueia.

1. Combinar uma janela de manutenção com os titulares; capturar os backups de **Rules reais** e de **Pages real** e congelar os SHA aprovados.
2. Publicar **primeiro as Rules restritivas** aprovadas, sob identidade operadora autorizada; verificar a nova release por leitura de confirmação. Se houver erro inesperado ou regras divergentes, **não** iniciar a publicação Web.
3. Na mesma janela, atualizar **somente o GitHub Pages existente** com o artefato aprovado e base `/teias-de-anansi/`. Não criar repo novo nem usar outra hospedagem. Se publicar exigir merge/push na `main`, usar exclusivamente a autorização específica correspondente.
4. Conferir em navegação anônima a tela de login sem dados; com testes realizados pelos próprios titulares, validar Mestre e quatro Jogadores, incluindo abertura por URL direta, atualização, logout, acesso permitido e negação cruzada. Usar apenas confirmações passou/falhou.
5. Monitorar erros de `permission-denied`, perda de sessão, inconsistência de membership, falha de consulta por listagem antiga e uso indevido de dados. Se qualquer autorização **indevida** for observada, suspender a liberação e priorizar **falha fechada**.
6. Encerrar a janela apenas após critérios de segurança e funcionamento aprovados, registrando release/hash/commit e data de publicação.

A sequência Rules-primeiro prioriza proteção de dados em detrimento de uma possível interrupção temporária do Pages antigo. **Não prometer atualização sem indisponibilidade**. Publicar o site primeiro mantendo Rules antigas não resolveria o problema de acesso direto a documentos e não é a sequência recomendada.

## 4. Plano de reversão sem relaxar permissões silenciosamente

| Falha após a mudança | Medida imediata | Limite |
| --- | --- | --- |
| Build/UI novos falham, mas Rules restritas estão corretas | Suspender acesso aos fluxos afetados, restaurar **artefato Pages aprovado** se for compatível com as Rules ou publicar no mesmo site uma página de manutenção **sem Firebase** (somente se previamente autorizado) | **Não** reabrir dados privados para manter UI antiga |
| A Rules candidata bloqueia leitura legítima crítica | Interromper a liberação do app, levantar a operação e corrigir **para frente** na candidata com teste em emulador e nova autorização | Não mudar dados legítimos para contornar regra |
| Aparece acesso indevido a perfil, ficha ou dados do Mestre | Parar imediatamente a liberação, manter/instalar proteção mais restritiva e registrar incidente sem dados sensíveis | Não fazer rollback automático para baseline permissiva |
| Novo login falha por domínio/Auth | Diagnosticar login e domínio sem redefinir senha, registrar evidência mínima, manter site em manutenção se necessário | Regras de Firestore não corrigem falhas de Authentication |
| Precisa restaurar Rules antigas por emergência | Comparar **backup efetivo da release imediatamente anterior**, riscos das 12 exposições históricas, janela, testes e autorização **específica para exceção** | **Nunca** usar `baseline.rules` como rollback automático; seria um possível retrocesso de segurança |

**Ordem de preferência:** corrigir para frente e manter acesso fechado; em caso de regressão visual, recuperar apenas a UI se ela funcionar com Rules restritas; **rollback de Rules inseguras exige decisão nova e explícita do usuário**.

Registrar o identificador das releases e os commits usados na ida e na volta. Nenhuma ferramenta deve executar os procedimentos por agendamento ou push automático.
